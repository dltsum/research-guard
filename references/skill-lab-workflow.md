# Skill research and ordinary use

Choose a component, install it, and ask for the work in ordinary language. Users
do not provide file fingerprints, state digests, event chains, signed receipts,
or hashes of messages. Existing saved records with those old fields remain
readable; their fingerprints do not control whether work may continue.

## Installing a domain Skill

Stage the selected content, scan the actual files for unsafe instructions, and
admit the Skill within its declared domain. Optimization and target-agent
research are optional. An installation without that research is recorded as
`NOT_EVALUATED`; installation does not imply an experimentally established gain.
Ordinary content edits do not invalidate the installation by fingerprint. The
content safety scan still checks the files being admitted, and installing a
Skill never automatically executes its third-party scripts.

## Optional research experiments

P24 evaluates a specified Skill on the submitted validation and held-out cases.
P25 measures transfer to the declared target cells. P26 compares the declared
no-Skill, single-Skill, target-order, and control-order conditions. Supply run
IDs, the cases, and the measured metrics. No artifact or execution checksum is
required. Rounds and replicates are selected by the task, default to one, and
may range from one to ten.

The scientific distinctions remain: missing runs are missing, held-out cases
must remain separate from development, metrics must be finite, and results do
not establish benefits outside the recorded conditions. Reusing the same run ID
as two independent runs is still rejected. An ordinary formatting or note edit
does not retroactively reject a recorded result.

## Records and reviews

Status reads summarize saved work. They do not traverse and fingerprint every
artifact on every call. Explicit verification checks the relevant files and
scientific states, such as an actual managed execution or the outcome of a
direction's coarse test. It does not require a matching historical byte hash.

Instruction waivers require the user's decision and a reason, without a message
checksum. Ordinary file edits do not invalidate a satisfied requirement. JSON
evidence that claims an execution passed is still checked for that actual
status. Delegation records retain the execution mode and provider boundary so a
local answer is not presented as an independent external review.

A single concrete correction or observed failure is sufficient to suggest an
improvement. The suggestion does not apply itself, and its validation is scoped
to the proposed change rather than a mandatory number of optimization cycles.
